## What is cloud computing?

On-demand delivery of computing services (servers, storage, databases, networking, software, analytics) over the internet with pay-as-you-go pricing — no owning physical hardware.

### NIST essential characteristics

| Characteristic | Meaning |
| --- | --- |
| On-demand self-service | provision resources automatically, no human interaction |
| Broad network access | available over the network from standard devices |
| Resource pooling | multi-tenant — one pool serves many customers |
| Rapid elasticity | scale up/down quickly (auto-scaling) |
| Measured service | usage monitored, billed on consumption |

**Memory trick:** On-demand, Broad access, Resource pooling, Elasticity, Measured → **O-B-R-E-M**.

## Service models

```text
SaaS — you use the app           (Gmail, Office 365)
PaaS — you deploy your code      (Heroku, App Engine)
IaaS — you manage OS + runtime   (EC2, Azure VMs)
FaaS — you write a function      (Lambda, Cloud Functions)
```

Ownership of everything below your layer belongs to the provider.

| Layer | You manage | Provider manages |
| --- | --- | --- |
| On-premises | everything | nothing |
| **IaaS** | app, data, runtime, OS | servers, storage, networking, virtualisation |
| **PaaS** | app, data | runtime, OS, servers, storage, networking, virtualisation |
| **SaaS** | nothing (just your data/usage) | everything |

- **IaaS examples:** Amazon EC2, Azure Virtual Machines, Google Compute Engine — rent VMs, install your own OS.
- **PaaS examples:** Google App Engine, Azure App Service, Heroku — push code, platform handles OS/scaling.
- **SaaS examples:** Gmail, Dropbox, Zoom, Salesforce — ready-to-use software.

<Callout type="tip">
Pizza analogy: on-prem = cook at home · IaaS = rent the kitchen · PaaS = get a pizza kit · SaaS = delivery. Exam order of control: IaaS most → SaaS least.
</Callout>

## Deployment models

- **Public** — shared infrastructure, multi-tenant (AWS, Azure, GCP).
- **Private** — single organisation, more control (a bank's internal cloud).
- **Hybrid** — public + private tied together (sensitive data private, burst capacity public).
- **Community** — shared by several organisations with common concerns (govt agencies for compliance).

Public = lowest cost / least control; private = highest cost / most control; hybrid sits in between.

## Shared responsibility (classic MCQ)

| Layer | Who patches |
| --- | --- |
| Data, app config | Customer |
| Guest OS in your VM | Customer |
| Hypervisor | **Provider** |
| Physical hosts, network, facilities | **Provider** |

<Callout type="warning">
"Who patches the hypervisor?" — always the cloud provider, never the customer. This exact question has appeared in multiple BD circulars.
</Callout>

## Elasticity & scaling

- **Vertical** scaling = bigger instance; **horizontal** = more instances.
- **Scalability** = handle increased load by adding resources (planned); **elasticity** = automatic scale up *and* down with real-time demand.
- Auto-scaling tracks load → cost efficiency + spike absorption.
- Pay-as-you-go converts capex to opex.

## Virtualisation & containers

One physical machine → multiple VMs via a **hypervisor**:

- **Type 1 (bare-metal)** — runs directly on hardware: VMware ESXi, Hyper-V (what data centers use).
- **Type 2 (hosted)** — runs on a host OS: VirtualBox, VMware Workstation.

| | VM | Container |
| --- | --- | --- |
| Virtualises | whole machine incl. guest OS | just the app layer (shares host kernel) |
| Size / boot | large (GBs), slower | small (MBs), seconds |
| Tools | VMware, VirtualBox | Docker, Kubernetes |

**Multi-tenancy** = many customers on shared infra, logically isolated. **Serverless** (AWS Lambda) = provider allocates servers for your event-driven functions; you pay only for execution time.

## Advantages & challenges

| Advantages | Challenges |
| --- | --- |
| Cost savings (no hardware) | internet dependency |
| Scale up/down easily | security & privacy of third-party storage |
| Access from anywhere | downtime risk on provider outages |
| Disaster recovery across sites | vendor lock-in |
| Provider-handled updates | limited control (especially SaaS/PaaS) |

## Well-architected pillars

Cost optimisation, security, reliability, performance efficiency, operational excellence, and sustainability — AWS's six pillars, echoed by Azure's well-architected framework.

<Callout type="info">
One-liners: IaaS = most control/most management · PaaS = write code, provider does the rest · SaaS = least control, easiest · Virtualisation makes the cloud possible · Docker = containers, AWS Lambda = serverless.
</Callout>
