## What is a Database & DBMS?

A **database** is a structured collection of data stored electronically — text, numbers, images, anything organised for easy access.

A **Database Management System (DBMS)** is software that sits between the database and its users/applications, handling storage, retrieval, updates and security in a structured way.

```text
User / Application
      ↓
   DBMS  (interface, security, recovery, concurrency)
      ↓
  Database (stored data)
```

**Core functions of a DBMS:**

- **Data management** — create, update and query data through a systematic interface instead of ad-hoc files.
- **Data integrity & security** — enforce rules and permissions so data stays consistent and private.
- **Concurrency** — many users can work at the same time without overwriting each other.
- **Reliability** — backup and recovery so a crash never loses committed work.

<Callout type="tip">
DBMS = the *manager* of the database. "Interface between database and users" is the one-line definition examiners look for.
</Callout>

## Problems with file-based systems

Before DBMS, data lived in plain files. The classic six problems:

| Problem | What goes wrong |
| --- | --- |
| **Data redundancy** | Same fact duplicated across files — student name stored in both academic and hostel files |
| **Data inconsistency** | Update in one file, not the other → conflicting versions of the truth |
| **Difficult access** | No query mechanism; finding one record means manual folder searching |
| **Poor security** | No access controls — anyone with file access sees everything |
| **Single-user access** | Files lock crudely; concurrent work risks corruption |
| **No backup/recovery** | Delete or corruption is usually permanent |

## Advantages & disadvantages of DBMS

**Advantages:**

1. **Reduced redundancy** — central storage, one copy of each fact.
2. **High security** — authentication, roles, permissions.
3. **Data integrity** — constraints block invalid values (age 200, GPA 5.0).
4. **Easy access** — SQL instead of manual file digging.
5. **Multi-user support** — concurrent transactions handled safely.
6. **Data sharing** — authorised users share data under DBA control.
7. **Standard enforcement** — consistent formats and naming.
8. **Backup & recovery** — automatic protection from failure.

**Disadvantages:**

1. **Complexity** — needs skilled designers and a DBA.
2. **Large size** — the engine itself consumes storage.
3. **Performance overhead** — extra layers vs raw files for tiny datasets.
4. **High impact of failure** — one crash can affect *all* applications.
5. **Cost** — licensing, hardware, maintenance.

<Callout type="info">
Trade-off in one line: DBMS buys security, integrity and sharing — paying with cost and complexity. For a single small flat file, a file system can still be simpler.
</Callout>

## Types of DBMS

| Type | Structure | Relationships | Example use |
| --- | --- | --- | --- |
| **Hierarchical** | Tree — parent–child | 1:1, 1:N only | old IMS, org charts |
| **Network** | Graph with pointers | M:N via links | CAD/CAM data |
| **Relational (RDBMS)** | Tables (relations) | Keys join tables | MySQL, Oracle, PostgreSQL |
| **Object-oriented (OODBMS)** | Objects with data + methods | Object references | multimedia, CAD |
| **Distributed (DDBMS)** | Split across network nodes | Transparent access | geographically spread data |

- **Hierarchical** — simple and fast for tree-shaped data, but a child has only one parent; complex relationships are awkward.
- **Network** — child can have many parents (fixes hierarchical's limit), but navigation via pointers makes applications fragile.
- **Relational** — rows = tuples, columns = attributes, keys define relationships; the dominant model, powered by SQL. Simple, flexible, set-based queries.
- **OODBMS** — stores objects directly (audio, video, complex types) with their methods; natural for OOP languages (Java, C++).
- **DDBMS** — data spread over multiple nodes; decentralised management improves availability, reliability and scale.

<Callout type="tip">
"Child can have only one parent" → hierarchical. "Child can have many parents via pointers" → network. "Everything today runs on this" → relational.
</Callout>

## Data models & DBMS architecture

### Data models

A **data model** is a set of conceptual tools describing data, relationships and constraints — the blueprint of a database.

Common models: **ER**, **relational**, **object-oriented**, **hierarchical**, **network**, **object-relational**, **flat**, **semi-structured** (XML/JSON).

The **relational model** stores data as tables: each row is a **tuple** (record), each column an **attribute** (property). Tables relate through **primary keys** and **foreign keys**.

| Student_Id | Name | Branch |
| --- | --- | --- |
| 1404001 | Misu | CSE |
| 1503002 | Avi | ETE |
| 1302119 | Rimon | CE |

This relation `STUDENT` has 3 attributes and 3 tuples.

### Architecture tiers

| Tier | Shape | Who talks to whom |
| --- | --- | --- |
| **1-tier** | user ↔ DBMS directly | developer on a local server; no network needed |
| **2-tier** | client ↔ database server | client holds UI + logic; server handles queries (ODBC/JDBC) |
| **3-tier** | client ↔ application server ↔ database | middleware holds business logic; better security & scalability |

More tiers = more **abstraction** — better security and flexibility, more complexity.

- **1-tier fits when:** data rarely changes, one user, or development/testing — e.g. MySQL installed on your own laptop while learning SQL, no network needed.
- **2-tier in the wild:** a bank teller's client app sends a withdrawal request straight to the DB server over **ODBC/JDBC**; the server checks the balance and replies. Direct and fast, but the client must be trusted.
- **3-tier:** large web apps put an application server (middleware) in the middle — it validates requests (integrity), holds business logic, and lets you scale app servers without touching the data tier.

### Levels of data abstraction

1. **Physical (internal)** — *how* bits are stored on disk (file structures, indexing).
2. **Logical (conceptual)** — *what* data exists: tables, relationships, constraints.
3. **View (external)** — what each user sees — a student sees grades, a teacher sees attendance.

<Callout type="tip">
"Which level describes disk layout?" → physical. "Which level shows only your subset?" → view. Architecture questions almost always test this three-level ladder.
</Callout>

## Schema vs instance

A **schema** is the static blueprint of the database — tables, columns, keys and constraints, designed up front. It changes rarely (DDL / migrations).

An **instance** is the actual rows sitting in the tables at one point in time — a snapshot. It changes with every `INSERT` / `UPDATE` / `DELETE`.

| | Schema | Instance |
| --- | --- | --- |
| What | structure / design | data content at a moment |
| Analogy | a blank form | the filled-in answers |
| Changes | rarely (DDL) | constantly (DML) |
| Example | `STUDENT(StudentID, Name, Branch)` | the rows present on 16 May vs 17 May |

Worked example: the `STUDENT` instance holds 2 rows on 16 May; on 17 May a new student (Rafi Hasan) inserts → 3 rows. **Same schema, different instances** — the same query run on the two dates returns different answers.

<Callout type="tip">
"Structure at design time" → schema. "Content at a moment" → instance. The words also label the three abstraction levels (external / logical / internal schema) — same ladder, different zoom.
</Callout>

## ER model essentials

An **ER diagram** models the logical structure of a database — entities, their attributes, and the relationships between them.

| Symbol | Represents | Example |
| --- | --- | --- |
| Rectangle | Entity | `STUDENT`, `COURSE` |
| Oval | Attribute | `name`, `roll_no` |
| Diamond | Relationship | `ENROLLS_IN` |
| Double oval | Multi-valued attribute | `phone_numbers` |
| Double rectangle | Weak entity | `DEPENDENT` |
| Double diamond | Identifying relationship of a weak entity | `HAS_DEPENDENT` |
| Underlined attribute | Primary key | `student_id` |
| Dashed oval | Derived attribute | `age` (from dob) |
| Single line | Partial participation | a student may take no courses |
| Double line | Total participation | every dependent needs its employee |

An ER diagram draws **entity sets** (all students), never individual instances.

**Attribute types:** simple vs composite (`name` → first, last), single vs multi-valued, stored vs derived (`age` derived from `date_of_birth`).

**Cardinality:**

- **1:1** — one to one (a person has one passport)
- **1:N** — one to many (one teacher teaches many students)
- **M:N** — many to many (students enrol in many courses)

**Participation:** *total* (every entity instance participates — each order has a customer) vs *partial* (some may not — a student may take no courses).

**Degree of a relationship:**

| Degree | Shape | Example |
| --- | --- | --- |
| Unary (recursive) | entity relates to itself | an employee manages another employee |
| Binary | two entity sets | student enrols in course — the common case |
| Ternary | three entity sets | supplier supplies product to project |
| N-ary | four or more | rare; prefer decomposing into binaries |

A **weak entity** (`DEPENDENT`) has no key of its own: it is drawn with a **double rectangle**, always sits in **total participation**, and connects through an **identifying relationship (double diamond)** to its owner — identified by a *partial key* plus the owner's key (`EMPLOYEE` + dependent name). A **ternary relationship** connects three entity sets — cardinality questions hinge on reading the notation correctly.

```text
[STUDENT] ---< ENROLLS_IN >--- [COURSE]
   |                                |
 (student_id, name)          (course_id, course_name)

Relationship attribute: enrollment_date
Cardinality: M:N
```

**ER → relational conversion:** entity → table, attributes → columns, 1:N and 1:1 relationships → foreign key on the "many"/one side, M:N → a **junction table** holding both keys as a composite primary key.

<Callout type="info">
Past-paper drill (tagged `CB, AP, 26`): *"Book ↔ Borrower — 1:1, 1:N or M:N? Justify."* Answer: **M:N** — one book is borrowed by many borrowers over time, one borrower borrows many books. Model it with an intermediate **Loan** table `(BookID, BorrowerID, borrow_date, return_date)` keyed on both IDs.
</Callout>

### Library Management System — full ER [AP pattern, 2023–2026]

The most repeated ER construction question. Entities, attributes, and cardinality:

```text
[MEMBER] ---< BORROWS >--- [BOOK]
   |                          |
(member_id PK, name,       (book_id PK, title,
 phone, join_date)          isbn, status)

[STAFF] ---< ISSUES >--- [LOAN] >--- [BOOK]
   |                        |
(staff_id PK, name)     (loan_id PK,
                          member_id FK, book_id FK,
                          issue_date, due_date, return_date)

[BOOK] ---1:N--- [AUTHOR]     M:N via [BOOK_AUTHOR]
[BOOK] ---1:N--- [PUBLISHER]
[BOOK] ---M:N--- [CATEGORY]   via [BOOK_CATEGORY]
```

**Cardinality summary:**

| Relation | Card | Why |
| --- | --- | --- |
| MEMBER : BOOK (direct) | M:N | many members borrow many books — needs junction |
| MEMBER : LOAN | 1:N | one member has many loan records |
| BOOK : LOAN | 1:N | one book issued many times over |
| STAFF : LOAN | 1:N | one librarian issues many loans |
| BOOK : AUTHOR | M:N | junction `BOOK_AUTHOR(book_id, author_id)` |

**ER → relational tables:** `MEMBER(member_id, …)`, `BOOK(book_id, …)`, `LOAN(loan_id, member_id FK, book_id FK, staff_id FK, …)`, `BOOK_AUTHOR(book_id FK, author_id FK)` composite PK. Loan is the textbook **relationship-as-entity** pattern.

## Keys & integrity constraints

| Key | Definition |
| --- | --- |
| **Super key** | any attribute set that uniquely identifies a row |
| **Candidate key** | minimal super key — no column can be dropped |
| **Primary key** | the chosen candidate key; NOT NULL, unique |
| **Alternate key** | a candidate key that was *not* chosen as primary |
| **Unique key** | like a primary key but nullable; several allowed |
| **Foreign key** | column referencing a primary/unique key in another table |
| **Composite key** | key made of two or more columns |

Worked enumeration on `STUDENT`: `{StudentID}`, `{StudentID, Name}`, `{StudentID, Email}`, `{StudentID, Name, Phone}` are all **super keys**; the minimal ones — `{StudentID}` and `{StudentID, Email}` — are **candidate keys**; pick one as **primary**, the other becomes an **alternate key**. A **unique key** (e.g. `Email`) allows NULLs, so it is weaker than a primary key.

A table can have many candidate keys but exactly **one** primary key.

**Integrity constraints:**

- **Entity integrity** — primary key can never be NULL.
- **Referential integrity** — every foreign key must match an existing referenced row, or be NULL (no orphans).
- **Domain constraint** — values must be of the right type/range (age ≥ 0).
- **Key constraint** — primary key values are unique.

**Assertions & triggers** go beyond row-level checks:

- An **assertion** is a global SQL condition the DBMS re-checks on *every* change — e.g. "total salary of dept ≤ budget". Expensive, rarely used.
- A **trigger** is procedural code that fires automatically on an event (`INSERT`/`UPDATE`/`DELETE`) — e.g. auto-fill an audit row. Stored procedures *you call*; triggers *the database calls*.

<Callout type="tip">
"Which constraint allows no NULL?" → entity integrity (on the PK). "What fires automatically after an UPDATE?" → trigger.
</Callout>

## Normal forms in one breath

**Normalization** organises data to reduce redundancy and avoid anomalies by splitting large tables into smaller related ones.

| Anomaly | Meaning |
| --- | --- |
| Insertion | Can't insert data without unrelated data present (can't add a course until a student enrols) |
| Update | Same fact repeated in many rows — must update all (advisor's phone in every student row) |
| Deletion | Deleting one fact accidentally deletes another (last student's row deletes the course too) |

1. **1NF** — atomic values only, one value per cell, no repeating groups.
2. **2NF** — 1NF + no *partial* dependency on a composite key.
3. **3NF** — 2NF + no *transitive* dependency of non-key attributes on the key.
4. **BCNF** — every determinant is a candidate key.
5. **4NF** — BCNF + no multi-valued dependency.

Formal **3NF test**: for every dependency `X → Y`, either `X` is a super key **or** `Y` is a prime attribute (part of some candidate key). Violates both → not 3NF.

<Callout type="tip">
TwoNF removes *partial*; threeNF removes *transitive*. One word each — learn them as pairs. Higher normal form = less redundancy but more joins; **denormalization** is the deliberate reverse for read-heavy reports. Real databases usually stop at 3NF or BCNF.
</Callout>

### Worked example — 1NF to 3NF

Micro-fix first — a phone column holding `98765432, 98123456` in one cell is not atomic; split to one row per value (`201 Alex` appears twice, `203 David` twice). That is 1NF.

Starting (not even 1NF — repeating groups):

| StudentID | StudentName | Course1 | Course2 | Advisor | AdvisorPhone |
| --- | --- | --- | --- | --- | --- |
| 101 | Akib | DBMS | OS | Dr. Rahman | 017xxxxxxx |
| 102 | Nadia | DBMS | — | Dr. Karim | 018xxxxxxx |

**1NF** — one course per row:

| StudentID | StudentName | Course | Advisor | AdvisorPhone |
| --- | --- | --- | --- | --- |
| 101 | Akib | DBMS | Dr. Rahman | 017xxxxxxx |
| 101 | Akib | OS | Dr. Rahman | 017xxxxxxx |
| 102 | Nadia | DBMS | Dr. Karim | 018xxxxxxx |

**2NF** — key is `StudentID + Course`; `StudentName` only needs `StudentID` (partial dependency) → split into **Student** `(StudentID, StudentName, Advisor, AdvisorPhone)` and **StudentCourse** `(StudentID, Course)`.

**3NF** — `StudentID → Advisor → AdvisorPhone` is transitive → split **Advisor** `(Advisor, AdvisorPhone)` out of Student.

## Dependencies & BCNF

If knowing a **Student ID** determines the **Student Name**: `StudentID → StudentName`. Read the arrow as "determines" — the left side must uniquely pin down one right side.

**Types of functional dependencies:**

| Type | Rule | Example |
| --- | --- | --- |
| **Trivial** | right side ⊆ left side — adds no information | `{Employee_Id, Name} → Name` |
| **Non-trivial** | right side not in left; the useful kind | `Employee_Id → Name` |
| **Multivalued** | double arrow `→→`; attribute holds many independent values | `Employee_Id →→ Phone` |
| **Transitive** | chain through another attribute | `Employee_Id → Zip → City` |

**Armstrong's axioms** (how dependencies are derived):

- **Reflexivity** — `A → A`
- **Augmentation** — `A → B` implies `AC → BC`
- **Transitivity** — `A → B` and `B → C` imply `A → C`

Closure, union and decomposition follow from these three.

**Partial dependency** — only possible with a *composite* (2+-column) key: the column needs only *part* of the key.

```text
Key = (StudentID, Course) but StudentName needs only StudentID
(A, B) → C, yet really A → C     → fixed in 2NF
```

**Transitive dependency** — a chain through another non-key column, even with a single-column key:

```text
StudentID → Advisor → AdvisorPhone     → fixed in 3NF
```

| | Partial | Transitive |
| --- | --- | --- |
| Key is | composite (2+ columns) | even single-column |
| Problem | column depends on only *part* of the key | non-key column depends on *another* non-key column |
| Pattern | `(A, B) → C` but really `A → C` | `A → B → C` |
| Fixed in | 2NF | 3NF |

### BCNF — stricter 3NF

For **every** dependency `X → Y`, `X` must be a super key. Classic example — each teacher teaches only ONE subject:

| Student | Subject | Teacher |
| --- | --- | --- |
| Akib | DBMS | Rahman |
| Akib | OS | Karim |
| Nadia | DBMS | Rahman |

Dependencies: `(Student, Subject) → Teacher` and `Teacher → Subject`. `Teacher` is not a super key but determines `Subject` → violates BCNF. **Fix:** split into `StudentTeacher(Student, Teacher)` and `TeacherSubject(Teacher PK, Subject)` — now `Teacher → Subject` is fine.

Every relation in BCNF is automatically in 3NF, but not vice versa — BCNF decomposition may not always preserve dependencies.

<Callout type="info">
For every arrow, ask: "Could the left side by itself uniquely identify a row (a candidate key)?" Yes for all → BCNF. No for even one → split the table.
</Callout>

## File organization & indexing

**File organization** decides how records sit on disk:

| Organization | Idea | Strength |
| --- | --- | --- |
| **Heap (unordered)** | records appended anywhere | fast inserts |
| **Sequential (sorted)** | records kept in key order | fast range scans, sequential access |
| **Hashed** | hash(key) → bucket/address | fastest equality lookups |
| **Indexed sequential** | sorted file + index | both equality and range |

**Indexing** keeps a side structure mapping key → record location so the DBMS skips full-file scans.

- **Primary index** — on the ordered file's key; one entry per block (**sparse**).
- **Dense index** — one entry per record; faster lookups, bigger index.
- **Sparse vs dense** — sparse = fewer entries (one per block, great for ordered files); dense = entry per record (works on unordered files too).
- **Secondary index** — on a non-key/unordered attribute; an extra indirection hop.
- **B+ tree** — balanced multi-level tree; all data only at leaves → more keys per node, clean range scans (`<`, `>`, BETWEEN).
- **Hash index** — `hash(key)` picks a bucket; excellent for `=`, useless for ranges. Extendible hashing / linear probing are the named variants.

<Callout type="tip">
Range query → B+ tree / ordered index. Equality query → hash index. "Index on a non-key attribute" → secondary index. Sparse needs an ordered file; dense does not.
</Callout>

## Transactions

A **transaction** is a single logical unit of work — one or more read/write/update/delete operations that must complete *entirely* or *not at all*. Transferring money from Account A to B (debit + credit) is one transaction: if either step fails, the whole thing fails.

### Transaction states

| State | Meaning |
| --- | --- |
| Active | Transaction is being executed |
| Partially committed | Last operation executed, changes not yet permanently saved |
| Committed | Completed successfully, changes saved permanently |
| Failed | Execution stopped due to error |
| Aborted | Rolled back, database restored to previous state |

### Key commands

- **COMMIT** — saves all changes permanently
- **ROLLBACK** — undoes changes if an error occurs
- **SAVEPOINT** — a point to roll back to, without rolling back the whole transaction

## ACID

- **Atomicity** — all or nothing; if debit succeeds but credit fails, the entire transaction rolls back.
- **Consistency** — the database moves from one valid state to another; constraints and relationships hold (total money in the bank is unchanged by a transfer).
- **Isolation** — concurrent transactions don't interfere; each behaves as if it were the only one running. Prevents **dirty read, non-repeatable read, phantom read** via isolation levels: Read Uncommitted, Read Committed, Repeatable Read, Serializable.
- **Durability** — once committed, changes survive crashes and power failures (WAL/force policy, logs and backups).

**Anomalies isolation must prevent:**

| Anomaly | Meaning |
| --- | --- |
| Dirty read | reading data another transaction hasn't committed yet |
| Non-repeatable read | re-reading a row gives a different value (someone committed in between) |
| Phantom read | re-running a query returns new rows (someone inserted) |

**One mini worked example per property:**

| Property | Worked example |
| --- | --- |
| Atomicity | debit $100 from A; if the matching credit to B fails, the debit rolls back — A unchanged |
| Consistency | a transfer never changes the bank's total; stock can't be driven negative by overselling |
| Isolation | two users race for seat `A1` — both read "free"; locking/serializability lets exactly one win |
| Durability | payment committed as "Saved" — a power cut one second later must not erase it (logs + force) |

<Callout type="tip">
Memory trick: A-C-I-D = *All Changes Isolated Durably*. "Which property is ensured by transaction logs?" → Durability.
</Callout>

## Concurrency control & deadlock

Concurrent transactions must produce the same result as *some* serial order — **serializability**.

- **Conflict serializability** — build a precedence graph of conflicting operations (same data, at least one write); no cycle ⇒ serializable.
- **Recoverable schedule** — a transaction commits only after the transactions it read from have committed.

### Lock-based protocols

| Protocol | Rule | Trade-off |
| --- | --- | --- |
| **Basic 2PL** | growing phase (acquire only), then shrinking (release only) | serializable, but can hold locks forever |
| **Strict 2PL** | hold exclusive locks until commit/abort | no cascading aborts — the practical choice |

- **Shared (S)** lock = readers; **Exclusive (X)** lock = writers; S and X conflict with each other.

### Deadlock — the four Coffman conditions

All four must hold **at the same time**; breaking any one prevents deadlock:

| Condition | Meaning | How it can be broken |
| --- | --- | --- |
| **Mutual exclusion** | a resource is held exclusively | rarely — locks are inherently exclusive |
| **Hold and wait** | holder waits while keeping another lock | acquire all locks up front |
| **No preemption** | locks can't be forcibly taken away | lock preemption / abort the holder |
| **Circular wait** | T1 waits for T2, T2 waits for T1 | impose a global lock-ordering rule |

Worked schedule: **T1** locks `STUDENT`, then asks for `GRADE`; **T2** locks `GRADE`, then asks for `STUDENT` → circular wait → deadlock until the DBMS intervenes.

### Handling strategies — four families

| Family | Idea | Named techniques |
| --- | --- | --- |
| **Prevention** | make a Coffman condition impossible | lock-all-upfront, ordered acquisition, **Wait-Die**, **Wound-Wait** |
| **Avoidance** | grant a request only if the system stays *safe* | safe-state check before each grant |
| **Detection** | allow it, find it, kill a victim | **wait-for graph** — cycle ⇒ abort youngest |
| **Ignoring** | pretend it's rare | **Ostrich algorithm** — what Windows & UNIX do |

**Wait-Die** (timestamp-based): an **older** transaction waits for a younger one; a **younger** transaction that would wait for an older one **dies** (aborts) and later restarts **with its original timestamp**.

**Wound-Wait**: an **older** transaction **wounds** (aborts) a younger holder and takes the lock; a **younger** transaction simply waits for an older one. Fewer restarts than Wait-Die when old transactions dominate.

**Wait-for graph detection:** nodes = transactions; edge `Ti → Tj` means Ti waits for Tj's lock. **Cycle = deadlock** (`T1 ↔ T2`, or `T1 → T2 → T3 → T1`). The scheduler picks a victim (youngest / least work done) and rolls it back.

### Alternatives to locking

*Timestamp ordering* assigns each transaction a timestamp and rejects out-of-date accesses; *MVCC* gives readers a snapshot so they never block writers (PostgreSQL, MySQL InnoDB).

<Callout type="tip">
"Which 2PL variant avoids cascading aborts?" → Strict 2PL. "Graph has a cycle?" → not conflict-serializable. Name all four Coffman conditions, and know Wait-Die vs Wound-Wait: **wait-die = young dies; wound-wait = young gets wounded** (only by an older txn).
</Callout>

## Query processing & cost estimation

The optimizer picks the cheapest plan for a query. Two costs dominate exam questions:

### Selection `σ`

| Plan | Cost idea | When |
| --- | --- | --- |
| **File scan** | read every block: `b` | no index |
| **Single-level index** | index probe + few block reads | equality `=` on indexed attr |
| **Multiple-level index** | `height × cost-of-probe` | big index |
| **Ordered index + range** | probe to start, then scan entries | `<`, `>`, BETWEEN |

Equality on a hashed key ≈ 1–2 I/Os; a file scan ≈ `b` I/Os (where `b` = blocks in the file).

### Join `⨝`

| Method | Cost sketch |
| --- | --- |
| **Nested loop** | `br × bs` block reads — fine for tiny outer relation |
| **Block nested loop** | `(br / buffer) × bs` — buffer the outer relation |
| **Index nested loop** | `br × cost of index probe on inner` — best when inner is indexed |
| **Sort-merge** | sort both (`br log br`) + merge linear — good for large inputs |
| **Hash join** | build + probe, roughly `2 × (br + bs)` — great for equality joins of similar size |

**Rule of thumb:** tiny outer + indexed inner → index nested loop; both huge, equality join → hash join; need sorted output → sort-merge.

<Callout type="info">
Costs are counted in **page/block I/Os** — CPU is assumed cheap in these formulas. `b` = blocks, `br`/`bs` = blocks of relations R and S.
</Callout>
