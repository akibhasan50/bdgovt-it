## What is Software Engineering

**Software Engineering** is the application of engineering principles to software — its development, operation, and maintenance. It treats software work as a measurable, repeatable process rather than ad-hoc coding.

### Why Software Engineering is needed

| Need | What it delivers |
|------|------------------|
| Portability & maintainability | Software that runs across environments and is easy to change |
| Reliability | Correct, consistent behaviour under expected conditions |
| High-quality products | Quality built into the process, not patched in at the end |
| Lower development cost | Reuse and planned processes cut rework |
| Reusability | Components used across projects save time |
| Time-to-market | Faster delivery of working software |
| Evolution / longevity | Software updated as requirements grow |
| Quality as a process | Quality measured and improved at every phase |

### Core attributes of SE work

Four attributes structure every SE project:

- **Requirement analysis** — what the system must do
- **Design** — how the system will be built
- **Coding** — writing the implementation
- **Testing** — finding and fixing defects before release

## Software Development Life Cycle (SDLC)

The **SDLC** is a structured process to design, develop, test, deploy, and maintain software. It exists so problems are solved systematically — analysis → design → coding → testing — and **software maintenance** consumes the largest share of the total cost because systems must keep working as needs change.

### SDLC phases

| Phase | Question it answers | Main output |
|-------|---------------------|-------------|
| Requirement Analysis | *What to build?* | Software Requirements Specification (SRS), reviewed with stakeholders |
| Design | *How to build?* | High-Level Design (HLD) and Low-Level Design (LLD) |
| Implementation | *Write the code* | Source code |
| Testing | *Find the defects* | Test results, defect reports |
| Deployment | *Deliver to users* | Live system |
| Maintenance | *Keep it running* | Patches, updates, improvements |

<Callout type="warning">
Exam trap: Requirement Analysis answers **What** to build; Design answers **How** to build. Do not swap them.
</Callout>

## Requirements Engineering

**Requirements Engineering** captures, analyses, documents, and validates what stakeholders need. **Market research** informs which features users actually want before work starts.

### Types of requirements

| Type | Focus |
|------|-------|
| Functional | Specific behaviours and functions of the system |
| Non-functional | Performance, security, usability, reliability |
| Business | Organisational rules and goals |
| User | What end users need to do their work |
| Implementation | Constraints on technology, platform, process |
| Interface | How the system talks to other systems |
| Regulatory | Legal and compliance constraints |
| Data reporting | Reports and data the system must produce |

### Prototyping

Building a preliminary model of the system lets stakeholders see and react to the design early.

**Advantages**
- Uncovers missing or wrong requirements before full development
- Improves communication with clients
- Reduces cost of late change cost

**Disadvantages**
- Can encourage scope creep if the prototype is treated as final
- Rapid throwaway models may ignore non-functional needs
- Extra effort if the prototype is built twice (throwaway + final)

### Functional vs security requirements — banking apps [AP pattern]

| | Functional requirement | Security requirement |
| --- | --- | --- |
| Asks | *What the system does* | *How the system is protected* |
| Banking example | "User can transfer funds between accounts" | "All transfers must be authenticated with 2FA and encrypted in transit (TLS)" |
| Verification | functional test / user acceptance | penetration test, security audit |
| Example set | balance inquiry, fund transfer, statement download | confidentiality of account data, integrity of transactions, availability of banking services (CIA) |

## Design Principles and Documents

### Three design principles

| Principle | Meaning |
|-----------|---------|
| Modularity | Break the system into independent, interchangeable modules |
| Abstraction | Hide detail; expose only what callers need |
| Encapsulation | Bundle data and methods; restrict direct access |

### SRS vs FRS vs BRS vs SDD vs HLD

| Pair | Difference |
|------|------------|
| **SRS vs FRS** | SRS is the full system requirements spec (all requirements, system-wide). FRS is the *functional* requirements spec — only what the software must *do*. |
| **SRS vs BRS** | SRS is technical and solution-oriented for developers. BRS (Business Requirements Specification) states *business* needs and goals for stakeholders. |
| **SDD vs HLD** | SDD (Software Design Document) documents overall design decisions. HLD (High-Level Design) focuses on system architecture and module-level structure. SDD is broader; HLD is the architectural view inside it. |

## Agile vs Waterfall [AP 2020, 2024]

| | Waterfall | Agile |
| --- | --- | --- |
| Flow | linear sequential phases, one at a time | iterative incremental sprints |
| Requirements | fixed up front in SRS | can change sprint to sprint |
| Customer involvement | at reviews / sign-off | continuous, every sprint |
| Delivery | single delivery at the end | working software every sprint |
| Testing | after each phase | continuous, test-driven |
| Best when | requirements are stable & well understood | requirements evolve; rapid delivery needed |
| Risk | late discovery of issues | harder to predict final date/cost |

**Git: commit vs push** — **commit** saves a snapshot of staged changes to your *local* repository history; **push** uploads committed history to the *remote* repository (e.g. GitHub) so others see it. Commit first, push second.

## Implementation and Programming

Good software starts with disciplined programming:

1. **Learn the basics** of at least one language
2. **Practice regularly** on real problems
3. **Understand fundamentals** — data structures, control flow, complexity
4. **Focus on problem-solving** before clever syntax

### Function as a Service (FaaS) benefits

- No infrastructure to manage — the platform runs the functions
- Teams focus on business logic only
- Automatic scaling with demand
- Quick updates and deployments

## Testing

Testing is a planned activity to **find defects** before users do.

### Purposes of testing

1. Find bugs and defects
2. Verify the software meets requirements
3. Ensure quality before release
4. Build stakeholder confidence
5. Validate performance, security, and usability
6. Prevent costly failures in production

### Levels of testing

| Level | Scope | What it checks |
|-------|-------|----------------|
| Unit testing | Individual functions/classes | Code coverage of each unit |
| Integration testing | Combined modules | APIs and interfaces between modules |
| System testing | Whole system | End-to-end, scenario-based behaviour |
| Acceptance testing | Against user needs | User needs and business needs are met |

### Testing methodologies

| Method | Approach |
|--------|----------|
| **Black box** | Test from the outside — inputs and outputs only; no knowledge of internal code |
| **White box** | Test inside the code — paths, conditions, statements (structural) |
| **Gray box** | Combination — some internal knowledge, mostly input/output focus |

<Callout type="info">
MCQ style: *debugging vs testing* — testing **finds** defects; debugging **fixes** them after they are found.
</Callout>

### Verification vs Validation [AME 2024–2026, CMMI L3]

| | Verification | Validation |
| --- | --- | --- |
| Question | *Are we building the **product right**?* | *Are we building the **right product**?* |
| Checks against | spec / design / standards | user needs & business requirements |
| Typical activities | reviews, inspections, unit tests, static analysis | system/acceptance tests, UAT demos, pilot |
| Timing | throughout development | at and near delivery |
| Failure means | implementation diverged from design | product solves the wrong problem |

**CMMI Level 3 (Defined)** — processes are documented, standardised, org-wide:

- Level 1 Initial (adhoc) → 2 Managed (project-specific) → **3 Defined (org standard)** → 4 Quantitatively Managed → 5 Optimizing
- **L3 process areas examiners name:** Requirements Development, Technical Solution, **Verification**, **Validation**, Integrated Project Management, Process/Product Quality Assurance, Decision Analysis
- At L3, verification & validation are **established organisational processes**, not one-off project heroics

## Software Maintenance

Maintenance is the largest cost in the SDLC. Three categories:

| Type | Trigger | Example |
|------|---------|---------|
| **Corrective** | Fix a reported defect | Patch a crash bug |
| **Adaptive** | Changed environment | Port to a new OS or library version |
| **Perfective** | Improved requirements | Add a feature or improve performance |

## Agile Software Development

**Agile** delivers software in small, iterative increments with continuous feedback.

**Benefits:** faster delivery, early feedback, easier requirement changes, closer customer collaboration.

### Agile lifecycle — 6 stages

1. **Planning** — scope, resources, timeline
2. **Concept / requirements** — what to build
3. **Iteration development** — build in short sprints
4. **Testing** — verify each increment
5. **Delivery** — release to users
6. **Production maintenance** — support and improve

### Process breakdown

Each iteration runs a mini-cycle: requirements → design → code → test → review → feedback into the next iteration. Cross-functional teams, daily stand-ups, and sprint reviews keep progress visible.

## Business Impact of Quality

### Qualitative factors

Organisations track business outcomes alongside technical metrics:

- Deliver **+20%** projects on time
- Drive **10%** of revenue from newly developed products
- Use **20%** of engineering capacity for platform rework

### Cost of quality

| Metric | Meaning |
|--------|---------|
| Defect rate | Defects per unit of work (e.g. per KLOC or per release) |
| Failure cost | Cost when defective software reaches production |
| Cost of control | Cost of prevention and appraisal (reviews, testing) |

Defect metrics tie **cost and schedule** to quality: more escaped defects raise failure cost and delay delivery.

### Function Point (FP) computation [BIBM / AP 2023]

Function Points measure functional size from the **user's** point of view — independent of programming language.

**Step 1 — count five components:**

| Component | What | Weights (simple / average / complex) |
| --- | --- | --- |
| EI (External Inputs) | data entering the system | 3 / 4 / 6 |
| EO (External Outputs) | reports, responses leaving | 4 / 5 / 7 |
| EQ (External Inquiries) | online queries, lookups | 3 / 3 / 4 |
| ILF (Internal Logical Files) | master files maintained inside | 7 / 10 / 15 |
| EIF (External Interface Files) | files maintained by other systems but referenced here | 5 / 7 / 10 |

**Step 2 — Unadjusted FP** = Σ (count × weight) for all fifteen cells.

**Step 3 — Value Adjustment Factor (VAF):**

```text
VAF = 0.65 + 0.01 × Σ  (14 General System Characteristics, each rated 0–5)
FP  = Unadjusted FP × VAF        (VAF ranges 0.65 … 1.35)
```

**Worked mini-example:** EI=4 avg (4×4=16), EO=2 avg (2×5=10), EQ=3 simple (3×3=9), ILF=2 avg (2×10=20), EIF=1 complex (1×10=10). Unadjusted = **65**. If Σ GSC = 40 → `VAF = 0.65+0.40 = 1.05` → **FP = 65 × 1.05 = 68.25 ≈ 68**.

## Past Exam Questions

**Q1:** Software Engineering (SE) is a systematic, disciplined, and quantifiable approach to the development, operation, and maintenance of software. Explain the statement. *(CB CE '23, '24)*

**A:** SE applies engineering methods to software work. *Systematic* means phased SDLC (requirements → design → code → test → deploy → maintain); *disciplined* means standards, reviews, and defined processes; *quantifiable* means metrics (defect rate, cost, schedule) guide decisions. Together they cover development, operation, and maintenance — not just coding.

**Q2:** What are the objectives/advantages of Software Engineering? What are the characteristics of software maintenance? *(CB AE'22, CE'21)*

**A:** *Objectives/advantages:* reliable high-quality software, lower cost through reuse and process, portability and maintainability, faster time-to-market, evolution over time. *Maintenance characteristics:* it is the costliest SDLC phase; ongoing after deployment; three types — corrective (fix defects), adaptive (environment changes), perfective (new/improved requirements).

**Q3 (MCQ):** Debugging is to testing as __ is to __. Options include: A) finding bugs / fixing them · B) fixing / finding · … *(CB AE'22)*

**A:** **A** — testing finds bugs; debugging fixes them.

**Q4:** Explain the SDLC phases with the question each phase answers.

**A:** Requirement Analysis — *What* to build (SRS); Design — *How* to build (HLD/LLD); Implementation — write code; Testing — find defects; Deployment — deliver; Maintenance — keep it running. Analysis is *what*, design is *how*.

**Q5:** What is prototyping? Give its advantages and disadvantages.

**A:** Building an early model of the system for feedback. *Advantages:* uncovers missing requirements, improves client communication, reduces late change cost. *Disadvantages:* risk of scope creep, may ignore non-functional needs, can mean building twice.

**Q6:** Compare black box, white box, and gray box testing.

**A:** Black box — inputs/outputs only, no code knowledge. White box — internal structure, path and condition coverage. Gray box — partial internal knowledge with mostly input/output focus.

**Q7:** List three design principles of software engineering.

**A:** **Modularity** (independent modules), **abstraction** (hide detail, expose essentials), **encapsulation** (bundle data + methods, restrict access).

**Q8:** Agile vs Waterfall — when would you choose each? *(AP 2020, 2024)*

**A:** Waterfall — linear phases, fixed requirements, single delivery; choose when requirements are stable and well understood. Agile — iterative sprints, evolving requirements, continuous customer involvement and early delivery; choose when requirements change and speed matters.

**Q9:** What is the difference between `git commit` and `git push`?

**A:** `commit` records a staged snapshot in your **local** repository history. `push` uploads local commits to the **remote** repository so others can see them.

**Q10:** Functional vs security requirements for a banking application.

**A:** *Functional* — what the system does (transfer funds, download statement). *Security* — how it is protected (2FA on transfers, TLS encryption, CIA of account data). Verified by functional tests vs penetration/security audits.

**Q11:** Compute function points for a system with EI=4 (avg), EO=2 (avg), EQ=3 (simple), ILF=2 (avg), EIF=1 (complex), Σ GSC=40.

**A:** Unadjusted = 4×4 + 2×5 + 3×3 + 2×10 + 1×10 = 16+10+9+20+10 = **65**. VAF = 0.65 + 0.01×40 = **1.05**. FP = 65 × 1.05 = **68.25 ≈ 68**.
