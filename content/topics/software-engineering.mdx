## Lifecycle models

- **Waterfall** — sequential, rigid, suits stable requirements.
- **Spiral** — risk-driven, iterative, heavier documentation.
- **Agile/Scrum** — iterations (sprints) of 1–4 weeks, daily standup ≤ 15 min, demo + retrospective each sprint.
- **Prototype** — build to clarify requirements.

## UML at a glance

UML is the standardised visual modelling language for designing and documenting object-oriented systems — **14 diagram types**: 7 structural (what the system *is*) + 7 behavioural (what the system *does*).

| Category | Diagrams |
| --- | --- |
| Structural | Class, Object, Component, Deployment, Package |
| Behavioural | Use Case, Sequence, Activity, State, Collaboration |

### Class diagram

Represents classes, attributes, methods and relationships. `+` public, `-` private, `#` protected.

| Relationship | Symbol | Meaning | Example |
| --- | --- | --- | --- |
| Association | Simple line | General connection | Student — Course |
| Aggregation | Hollow diamond | "has-a" (weak) | Department – Professor |
| Composition | Filled diamond | "part-of" (strong) | House – Room |
| Inheritance | Hollow triangle | "is-a" | Animal – Dog |
| Dependency | Dashed arrow | Uses temporarily | Order – Payment |
| Multiplicity | Numbers on ends | `1`, `0..1`, `1..*`, `*` | — |

### Use case diagram

Shows functional requirements — actors and what they can do.

- Stick figure = **actor**, oval = **use case**, rectangle = system boundary
- `<<include>>` → one use case *always* uses another (Withdraw Cash always requires Login)
- `<<extend>>` → optional/conditional behaviour (Print Receipt is optional)

### DFD (Data Flow Diagram)

Shows how **data moves** through a system — never control flow or timing.

| Symbol (Yourdon/DeMarco) | Represents |
| --- | --- |
| Circle / rounded rectangle | Process |
| Rectangle | External entity |
| Open rectangle / parallel lines | Data store |
| Arrow | Data flow |

- **Level 0 (context diagram)** — the whole system as one process
- **Level 1** — major sub-processes
- **Level 2+** — further breakdown

<Callout type="tip">
Quick comparison: ER → database design · Use case → functional requirements · DFD → data movement · Class diagram → static OOP structure. "Which diagram shows actors?" → use case.
</Callout>

## Testing taxonomy

| Level | Target |
| --- | --- |
| Unit | individual functions/classes |
| Integration | module interactions |
| System | end-to-end workflows |
| Acceptance | customer requirements |

By technique: **black-box** (spec-based: equivalence partitioning, boundary value) vs **white-box** (structural: statement/branch coverage). Sanity vs smoke: smoke = broad shallow "does it start?"; sanity = targeted "does this fix work?".

<Callout type="tip">
"Testing without knowing internal code" → black-box. That one sentence answers most testing MCQs.
</Callout>

## Estimation & metrics

Function points and COCOMO for effort; use-case points for OO. Cyclomatic complexity = E − N + 2P — independent paths through code.

## Version control in practice

```bash
git clone / init / status
git add . && git commit -m "msg"
git push origin feature-x     # upload
git pull                      # fetch + merge
git merge main                # bring main INTO your branch
git rebase main               # replay your commits on top
```

Branch-per-feature, PR review, `.gitignore`, semantic commits — expected knowledge in any BD IT interview.

<Callout type="info">
CI runs builds/tests on every merge; CD deploys automatically. "What does CI/CD stand for" still appears in screening exams.
</Callout>
