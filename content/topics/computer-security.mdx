## CIA triad [AP pattern, 2023–2026]

The three pillars every security question maps to:

| Pillar | Goal | Attack that breaks it | Control |
| --- | --- | --- | --- |
| **Confidentiality** | only authorised parties read | sniffing, eavesdropping, theft | encryption, access control |
| **Integrity** | data unaltered & accurate | MITM tampering, malware | hashes, MACs, digital signatures |
| **Availability** | systems up when needed | DDoS, ransomware | redundancy, backups, rate limiting |

## Cryptography

| Property | Symmetric | Asymmetric |
| --- | --- | --- |
| Keys | one shared | public + private pair |
| Examples | AES, DES, 3DES | RSA, ECC, Diffie–Hellman |
| Speed | fast | slower |
| Use | bulk encryption | key exchange, signatures |

<Callout type="tip">
"AES vs RSA" questions are almost always about symmetric vs asymmetric classification. AES = symmetric — memorise that pairing.
</Callout>

## Hashing

- **MD5** — 128-bit, broken.
- **SHA-1** — 160-bit, deprecated.
- **SHA-256** — 256-bit, SHA-2 family, current standard.
- **bcrypt** — password hashing with cost factor (not encryption).

Hashes verify integrity; digital signatures (hash + private key) also authenticate the sender.

### Spoofing vs sniffing — the paired MCQ

| | Spoofing | Sniffing |
| --- | --- | --- |
| Action | *impersonates* a trusted source (fake IP, MAC, email) | *passively captures* packets on the wire |
| Goal | gain access / redirect traffic | steal credentials, map the network |
| Type | **active** attack | **passive** attack |
| Example | ARP spoofing, phishing from a look-alike domain | Wireshark capturing HTTP passwords on open LAN |
| Counter | anti-spoofing filters, ARP inspection, MFA | encryption (TLS/VPN), switch port security |

### MITM on Diffie–Hellman key exchange

DH authenticates **nobody**. An attacker sits in the middle, opens one DH conversation with each party, and relays modified messages — each side believes it shares a key only with the other, while the attacker shares keys with both and can read/modify everything.

**Fix:** **authenticate** the DH public keys (digital signatures / certificates inside TLS). Pure unauthenticated DH is wide open to MITM.

### TLS/SSL private-key exposure

If the server's **private key** leaks: attacker can **impersonate the server** to any client, and — without forward secrecy — **retroactively decrypt recorded traffic**. Rotate the cert immediately. **DHE/ECDHE** key exchange provides **forward secrecy**: past sessions remain safe even if the long-term private key is later stolen.

### Same-Origin Policy (SOP)

Browser rule: script from `https://bank.com` may only freely access resources from the **same origin** (scheme + host + port). Cross-origin reads are blocked unless the target opts in via **CORS**. Primary defence against a malicious third-party page reading your logged-in banking session.

Firewall filters traffic by rules; **IDS** alerts, **IPS** drops; DMZ isolates public services.

<Callout type="tip">
"Passive capture" → sniffing · "Fake identity" → spoofing · "DH with no auth" → MITM · "Cross-site data read blocked by browser" → Same-Origin · "Leaked server key" → past + future impersonation (use ECDHE for forward secrecy).
</Callout>

## Banking transaction security [AME 2024–2026]

### Atomicity in EFT/RTGS — the ACID question

Fund transfer A→B must happen **completely or not at all**:

| Failure point | Without atomicity | With atomicity (ACID-A) |
| --- | --- | --- |
| Debit done, credit crashes | money vanishes | debit **rolled back** — account unchanged |
| Partial multi-leg transfer | inconsistent balances | journal/WAL forces both-or-neither |

**Atomicity** = all-or-nothing (transaction log + rollback). Complements **Consistency** (constraints hold), **Isolation** (concurrent transfers don't interleave wrongly), **Durability** (commit survives power loss). *"Inter-bank fund transfer requires which ACID property?"* → **Atomicity**.

### MFA, OTP & digital signatures

| Factor type | Examples |
| --- | --- |
| Something you **know** | password, PIN |
| Something you **have** | OTP on phone, hardware token |
| Something you **are** | fingerprint, face, iris |

**MFA** = at least two *different* factor types. Bank OTP channels: **SMS, push notification, authenticator app (TOTP), email** — SMS is weakest (SIM-swap), app/TOTP preferred.

**Digital signature** = hash(message) encrypted with sender's **private key** → receiver verifies with sender's **public key**. Gives integrity + authentication + non-repudiation (not confidentiality — the message itself is often only hashed, not encrypted).

### Firewall depth — stateful vs NGFW vs WAF

| Layer | What it protects | Exam keyword |
| --- | --- | --- |
| Packet-filtering | IP/port headers | ACL rules |
| **Stateful** | connection state tables | established sessions |
| **NGFW** | DPI + IPS + app/user ID | "deep packet inspection" |
| **WAF** | web app HTTP layer | SQLi, XSS, OWASP top 10 |
| IDS/IPS | anomaly/malware signatures | detect vs prevent |

### ISO/IEC 27001 & IT audit flags [AME 2024–2026]

ISMS standard for information-security management. **Audit violation scenarios papers love:**

| Scenario | Verdict | Why |
| --- | --- | --- |
| Shared superuser (root/admin) password across staff | **violation** | no accountability, breaks least-privilege & unique-ID controls |
| Backup only weekly for transaction DB needing daily | **violation** | RPO too large vs stated policy |
| Root login over SSH with password (no key) | **violation** | weak authentication for highest privilege |
| Firewall rule `allow any any` on DMZ | **violation** | no least-privilege segmentation |
| Documented DR test twice a year with evidence | **compliant** | policy met, auditable |

Controls map to CIA + accountability: unique user IDs, need-to-know access, encryption in transit/at rest, logged privileged actions, scheduled tested backups.

### Malware family [BKKB AP 2026]

**Q: Which software steals data and sends it to a remote user?**

**Answer:** **Spyware**

**Explanation:** spyware runs covertly on the host, records activity (keystrokes, screens, files, credentials) and **exfiltrates it to an attacker-controlled server**. The user rarely notices — no obvious "infection" symptom, which is why it differs from ransomware.

**Full family table:**

| Type | What it does | How it spreads | Exam keyword |
| --- | --- | --- | --- |
| **Spyware** | monitors & **ships data to a remote attacker** | bundled freeware, drive-by download | *steals data → remote user* |
| Virus | corrupts files/programs | needs a **host file** + user action (open/execute) | attaches to carrier |
| Worm | self-replicates across networks | **no host file**, exploits network services | spreads by itself |
| Trojan | looks legitimate, runs malicious payload | social engineering, fake apps | trust/disguise |
| Ransomware | encrypts data, demands payment | phishing, RDP brute force | CIA → availability |
| Adware | injects ads, tracks clicks | bundled installers | annoying, often legal-grey |

**Related info:**

- **Rootkit** — hides itself (and other malware) from the OS/admin tools; deep persistence.
- **Keylogger** — specialised spyware for keystrokes only.
- **Botnet** — compromised machines under remote command (DDoS army).

**Exam tip:** the giveaway phrase is always **"sends stolen data to a remote user"** → **spyware**. If the stem says *"disguised as useful software"* → **Trojan**. If *"spreads without user opening a file"* → **worm**.

<Callout type="tip">
BKKB AP 2026 wording: *"Which software steals data and sends it to a remote user?"* → **Spyware**. Pair it with Trojan (disguise) and Worm (autonomous network spread) — those three are the usual MCQ distractors.
</Callout>

## PKI & legal basics

Certificate Authority issues TLS certs chaining to a trusted root. Bangladesh's **Digital Security Act 2018** (now succeeded by the Cyber Security Act 2023) criminalises unauthorised access and cyber offences — know the year the current act was enacted.
