## What OOP is — and why exams ask it

[NTRCA-2014, BOF-2018] Object-oriented programming models software on real-world entities: a **class** is the blueprint (data members + member functions), an **object** is one instance of it. An application divides into packages → classes → objects. Languages tagged as OOP in papers: Python, C++, Java, Visual C, Visual Basic.

The four pillars, as a one-line exam answer each:

| Pillar | One-line exam answer |
| --- | --- |
| Encapsulation | Bundle data + methods, hide internals behind access modifiers |
| Abstraction | Expose only the necessary interface |
| Inheritance | Derive new classes from existing ones (code reuse, "is-a") |
| Polymorphism | Same message, different behaviour (compile-time or runtime) |

### The four pillars — proper descriptions

**Encapsulation** wraps data (fields) and the methods that operate on that data into a single unit (the class) and restricts direct access to the internals with access modifiers (`private` / `protected` / `public`). Outside code calls public methods; private state never leaks. Also called **data hiding**. Why it matters: integrity (only validated paths can change state), easier debugging (change is local), safer team work (interfaces stay stable while internals evolve).

**Abstraction** shows *what* an object does, not *how*. You drive a car with steering and pedals — you never touch the combustion cycle. In code, abstract classes and interfaces define the contract; concrete subclasses implement the details. Related tools: `abstract` methods (must be overridden), interfaces (pure contract in classic Java), pure virtual functions in C++.

**Inheritance** lets a subclass acquire fields and methods of a superclass: code reuse + an **"is-a"** relationship. Covered in full below — five types, Java vs C++ support, diamond problem.

**Polymorphism** = "many forms": the same message (method call, operator) produces different behaviour depending on the runtime type. **Compile-time polymorphism** = overloading (and templates/generics). **Runtime polymorphism** = overriding through a base reference (`Animal a = new Dog(); a.eat();`). Needs inheritance for the runtime form.

Nine standard advantages over procedural style — memorise the headline words:

| Advantage | One-line reason |
| --- | --- |
| Modularity & reusability | program split into small reusable objects |
| Encapsulation | data + methods bundled; internals hidden |
| Abstraction | only essential features exposed |
| Inheritance | new classes reuse old properties |
| Polymorphism | same function, different behaviour |
| Flexibility & scalability | large systems stay manageable |
| Easy maintenance | change one class without ripple effects |
| Team development | developers own different classes |
| Real-world modeling | objects mirror real entities |

<Callout type="tip">
"Write the advantages of OOP over structured programming" is a recurring written question (CB Officer IT 2023). Lead with modularity, reusability, encapsulation, abstraction, maintainability, scalability, real-world modeling.
</Callout>

## Structured vs object-oriented [45 BCS]

| Structured | Object-oriented |
| --- | --- |
| Focus on functions/procedures | Focus on objects and classes |
| Data and functions separate | Data + functions combined |
| No inheritance / polymorphism | Both supported |
| Less data hiding | Data hiding & security |
| Small programs | Large, complex systems |
| Example: C | Example: C++, Java |

Class vs structure is the same contrast one level down: a structure groups plain data (default public, no polymorphism), a class bundles data **with** methods, enforces access control, and participates in inheritance.

## The six properties [BPDB-2004, BOF-2018, NTRCA-14/16/19/20, Uttara Bank-2019]

1. **Class** — user-defined type; blueprint with data members and member functions (Car: wheels, speed, mileage shared by all cars). Not a built-in type — you define structure and behaviour once, then instantiate.
2. **Object** — instance of a class with **identity** (unique name/reference), **state** (current field values), **behavior** (methods it can run). Dog: state color/breed; behavior bark/eat. Class is the recipe; object is the cake.
3. **Abstraction** — essential features only; hide implementation detail. Driving uses accelerator/brake without engine knowledge. Implemented with abstract classes, interfaces, and access control.
4. **Encapsulation** — data + methods in one unit, access restricted — also called **data hiding**; bank balance reachable only through `deposit`/`withdraw`. Combines binding + restriction (abstraction is the design goal; encapsulation is the mechanism).
5. **Inheritance** — child acquires parent properties and behaviours; code reuse and "is-a" (Animal → Dog inherits eat, sleep, then adds bark). Five shapes: single, multilevel, multiple, hierarchical, hybrid.
6. **Polymorphism** — many forms; **compile-time → overloading, run-time → overriding**. Same person as father/employee/husband — same reference type, different concrete behaviour.

## Encapsulation in code

Data stays `private`, touched only through `public` methods — the outside world cannot bypass validation:

```cpp
class BankAccount {
private:
  double balance;
public:
  void deposit(double amount)  { balance += amount; }
  void withdraw(double amount) { if (balance >= amount) balance -= amount; }
  double getBalance()          { return balance; }
};
```

[Combined Bank O(IT) 2024] Advantages of encapsulation: data security, easy maintenance, better flexibility, less complexity, easier debugging. Advantages of inheritance: code reusability, clear structure, easy expansion, simpler management.

## Access specifiers

| Specifier | Visible where |
| --- | --- |
| `public` | anywhere |
| `private` | only inside the class |
| `protected` | class + derived classes (inheritance) |

Skeleton: `class ClassName { private: ... public: ... protected: ... };` — sensitive data private, general members public, members meant for subclasses protected. That is data hiding implemented.

## Inheritance & its vocabulary [NTRCA-14, PSC-17, ICB-17 MCQ]

**Inheritance** allows a class (**subclass / derived class**) to acquire the **properties and behaviours** (fields and methods) of another class (**superclass / base class**), promoting **code reuse** and establishing an **"is-a"** relationship — Dog *is an* Animal, so Dog inherits `eat`, `sleep` without rewriting them.

```cpp
class A { public: int x = 10; void print() { cout << "Hello" << endl; } };
class B : public A {};   // B b; b.print(); uses inherited members
```

ICB-17 tests the synonyms directly: Super = Parent = Base; Derived = Child = Subclass.

**Core benefit across all types:** write shared behaviour once in the superclass; every subclass reuses it. A subclass object can also be treated as its superclass type — `Animal a = new Dog();` — which is the bridge into runtime polymorphism.

### Types of inheritance

| Type | Structure | Java support | C++ support |
| --- | --- | --- | --- |
| Single | 1 parent → 1 child | Yes | Yes |
| Multilevel | chain of 3+ classes | Yes | Yes |
| Hierarchical | 1 parent → many children | Yes | Yes |
| Multiple | 1 child ← 2+ parents | No (interfaces only) | Yes |
| Hybrid | combination of the above | Partial (via interfaces) | Yes |

#### 1. Single inheritance

One subclass extends exactly one superclass.

```java
class Animal {
    void eat() { System.out.println("Animal eats"); }
}
class Dog extends Animal {
    void bark() { System.out.println("Dog barks"); }
}
// Dog dog = new Dog(); dog.eat(); dog.bark(); — both work
```

C++ form: `class Dog : public Animal {};`

#### 2. Multilevel inheritance

A chain: each class inherits from the previous one.

```java
class Animal {
    void eat() { System.out.println("Animal eats"); }
}
class Mammal extends Animal {
    void walk() { System.out.println("Mammal walks"); }
}
class Dog extends Mammal {
    void bark() { System.out.println("Dog barks"); }
}
// Dog inherits eat() from Animal AND walk() from Mammal — both levels up the chain
```

Constructor order = chain order: Animal → Mammal → Dog — parent constructors run first.

#### 3. Multiple inheritance

One class inherits from two or more superclasses.

```cpp
// C++ — direct
class Flyable  { public: void fly()  { cout << "Flying";  } };
class Swimmable { public: void swim() { cout << "Swimming"; } };
class Duck : public Flyable, public Swimmable { };
// Duck has both fly() and swim()
```

```java
// Java — via interfaces, since Java disallows multiple class inheritance
interface Flyable  { void fly(); }
interface Swimmable { void swim(); }
class Duck implements Flyable, Swimmable {
    public void fly()  { System.out.println("Flying"); }
    public void swim() { System.out.println("Swimming"); }
}
```

```cpp
// Compact exam sketches
class B : public A {};                 // single
class C : public B {};                 // multilevel   (A → B → C)
class D : public A, public B {};       // multiple     (C++ direct; Java → interfaces)
```

#### 4. Hierarchical inheritance

One superclass, many independent subclasses (siblings).

```java
class Animal {
    void eat() { System.out.println("Animal eats"); }
}
class Dog extends Animal { void bark() {} }
class Cat extends Animal { void meow() {} }
class Bird extends Animal { void fly()  {} }
// Three siblings all reuse Animal's eat(), each adds its own behaviour
```

Each child fires the shared Animal constructor when created.

#### 5. Hybrid inheritance

Any **combination** of the above — e.g. hierarchical + multilevel: `Animal → Mammal`, then fan-out `Mammal → Dog` and `Mammal → Cat` (multilevel down to Mammal, hierarchical from there). Common in real layered "is-a" hierarchies. In C++ a pure diamond hybrid needs **virtual inheritance** to keep one shared base; in Java you model the same shape with interfaces.

```text
      Animal
         |
      Mammal          ← multilevel to here
      /    \
    Dog    Cat        ← hierarchical fan-out
```

### Diamond problem & Java's answer

```text
        Parent
        /   \
   Child1  Child2
        \   /
      GrandChild
```

Both paths carry `Parent::sum()` — GrandChild wouldn't know which version to use: **ambiguity**. If B and C each override a method from A differently, D inherits two conflicting implementations. **Java refuses multiple inheritance with classes** for exactly this reason and only allows multiple inheritance through **interfaces** (historically method signatures only; default methods now require explicit conflict-resolution rules). **C++ fixes the diamond with virtual inheritance.**

<Callout type="warning">
Ambiguity, not performance, is the stated reason Java bans multiple class inheritance. Exam phrasing: "Why multiple inheritance is not supported in Java?" → answer = ambiguity problem, solved by interfaces.
</Callout>

## Polymorphism [CB-24, PSC-25, NTRCA-14, BB-14, PSC-17]

"Poly" many + "morph" forms — same interface or message, different concrete behaviour. The operator `+` adds `10 + 32 → 42` and concatenates `"poly" + "morphism"` — one operator, multiple behaviours. Without polymorphism you would need name-different methods for every type; with it, callers stay type-agnostic.

| | Compile-time (static) | Run-time (dynamic) |
| --- | --- | --- |
| Also called | early binding | late binding |
| Mechanism | function & operator overloading | virtual functions & overriding |
| Inheritance needed | no | yes |
| Speed | faster | slightly slower |
| Flexibility | less | more |

### Function overloading [BB-2014, 17, BPSC-2019]

Same name, different parameter **count or type** — never return type alone:

```cpp
class Temp {
  int x = 10; double x1 = 10.1;
public:
  void add(int y)        { cout << x + y << endl; }
  void add(double d)     { cout << x1 + d << endl; }
  void add(int y, int z) { cout << x + y + z << endl; }
};
// t.add(10); t.add(11.1); t.add(12, 13);  → 20, 21.2, 35
```

### Operator overloading [NTRCA-2014, IP-2014]

Redefine operators for user-defined types. Rules:

- At least one operand must be a user-defined type.
- **Cannot overload:** `.` , `::` , `?:` , `sizeof` , `typeid`.
- Overloadable: arithmetic `+ - * / %`, relational `== != > < >= <=`, logical `&& ||`, bitwise `& | ^ << >>`, `new`, `delete`.

## Overriding, virtual, pure virtual [BB-2014]

Overriding = child redefines a parent method with the **same signature** so the runtime type picks the implementation. Without `virtual`, calls bind at compile time — a `Polygon*` pointing at a Rectangle still prints the **base** area (0, 0, 0). With `virtual`, the same pointers print 200 / 100 / 0: correct dispatch at runtime.

```cpp
class Base { public: virtual void func() = 0; };  // pure virtual → abstract class
```

Derived **must** implement `func()`, else compilation fails. A class with any pure virtual function cannot be instantiated — same rule as a Java `abstract` class with an `abstract` method.

<Callout type="tip">
A single MCQ often tests the pair: overloading → compile-time polymorphism; overriding → runtime polymorphism. "Method hiding" (static) is neither — statics hide, they do not override.
</Callout>

### Overloading vs overriding [ABL-17, NTRCA-2011]

| Overloading | Overriding |
| --- | --- |
| Redefine by changing signature | Redefine base method in derived class |
| Compile-time | Runtime |
| Parameters must differ | Signature must match |
| Same scope | Different scopes (parent/child) |
| No inheritance required | Requires inheritance |
| Can overload many times | Overridden once |

BB-2013 style: identify all three — **overloading** (same class, different params, non-static), **overriding** (subclass non-static same signature, runtime), **hiding** (subclass `static` same signature, compile-time).

## Constructors & destructors

Constructor: same name as class, **no return type**, runs automatically on creation, initialises members. Three kinds:

| Type | Signature idea | Note |
| --- | --- | --- |
| Default | no parameters | compiler generates one if you write none |
| Parameterized | takes arguments | define only this → must always pass arguments |
| Copy | `ClassName(ClassName &obj)` | copies from a same-class object; compiler supplies implicit version |

```cpp
class Example { public: int a, b; Example() { a = 10; b = 20; } };
// Example obj; → prints 10 20
```

Destructor `~ClassName()`: no parameters, no return type, cannot be overloaded, runs **LIFO** — reverse of constructor order. Use it to free memory, close files, release resources.

| Constructor | Destructor |
| --- | --- |
| Initialises object | Cleans up on destruction |
| `ClassName()` | `~ClassName()` |
| May take parameters | Never takes parameters |
| Overloadable, many allowed | Exactly one, not overloadable |

In C++ destructors run bottom-up during `super()`-style chains; objects live on the heap while references live on the stack.

## Java modifiers worth memorising

```java
final class A {}      // cannot be extended
final void m() {}     // cannot be overridden
abstract void m();    // must be overridden, class must be abstract
static void m() {}    // belongs to class, no overriding (hides instead)
```

## Design patterns that appear

- **Singleton** — one instance, private constructor, global access point.
- **Factory** — delegating instantiation to a creator method.
- **Observer** — one-to-many dependency notification.

You rarely implement these in MCQs; you identify them from a two-line description.
